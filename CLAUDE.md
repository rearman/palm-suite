# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Layout

One jj repository (colocated with git, remote `rearman/palm-suite`) with one Gradle build of five modules, and the Go sync server. The Date Book and launcher histories came in by subtree merges from the archived repos `rearman/datebook` and `rearman/palm-launcher`. Read the `CLAUDE.md` of the app you change before you work in it.

## Shared conventions

- `sync-server/` is a Go module with the standard library only, outside the Gradle build. The CI `server` job runs `gofmt`, `go vet` and `go test`. A tag `server-v*` attaches the linux amd64 and arm64 binaries to its release. This machine has no Go, so CI also verifies the server.
- `sync-core/` is a plain Kotlin/JVM module (JDK 17) with no runtime dependency; it uses the `org.json` that Android has built in, and its tests add `org.json`. CI tests `:sync-core:test` in the build job. Date Book's model, iCalendar and sync logic live in sync-core in the package `com.rearman.datebook`, so Date Book code uses them with no import. `WearAgenda` is the payload codec that Date Book and its watch app share; it is Android only, so the C++ port has no copy. The Swing desktop app (`desktop/`, versions up to 0.23) is gone since the cutover to the C++ app in 0.24; its history stays in jj.
- `desktop-cpp/` is a CMake project outside the Gradle build: Palm Desktop for Windows and Linux in C++23 and FLTK, the shipped desktop app since 0.24. It was ported module by module from a Rust and fltk-rs app (removed after the cutover; see the jj history), so comments and `PLAN.md` still name the Rust files and fltk-rs calls each part came from. `core/` is the port of sync-core: one static library per module, with doctest tests that check it against `sync-core/testdata`, port SyncRunnerTest and SyncSessionTest, and sync two devices through a real palmsync when `PALMSYNC_URL` and `PALMSYNC_TOKEN` are set. `app/` is the desktop app (`palm-desktop`): the store and the settings read and write `desktop-data.json` and `desktop.properties` (the files of the Swing app up to 0.23), a lock file keeps a second copy from overwriting the data (a Swing app takes no lock, so do not run one beside it), `platform` gives the local zone (with the CLDR Windows table) and the OS error texts, and `test_store` checks copies of real files when `PALM_REAL_DATA` names their folder; the files never go into the repository. The UI: the shell (`window.cpp`: main window, menus, toolbar, launcher bar, status bar, sync with Sync Options), the Windows classic edges drawn in device pixels (`draw.cpp`), the Memo Pad (`memo.cpp`), the detail split (`split.cpp`), the category drop-downs and Edit Categories (`category.cpp`), the record clipboard, list menu and list events (`records.cpp`), the text-field menu and Edit state (`text_edit.cpp`), the modal dialogs (`dialogs.cpp`, each runs its own event loop), the Address Book (`address.cpp`, `address_dialog.cpp`; Dial opens a `tel:` link), the To Do List (`todo.cpp`, whose rules of order, due labels and completion serve the Day view too), the date dialog (`date_picker.cpp`), the Note Editor (`note_dialog.cpp`), the Date Book (`date.cpp` and `date_view.cpp`, which share `app/src/date_internal.hpp`; `week.cpp`, `month.cpp`, `event_dialog.cpp`, `date_shared.cpp`), Find (`find.cpp`), Import and Export (`transfer.cpp`), Print (`printing.cpp`, through the system print dialog) and Options (`options.cpp`); Page Setup stays gray, since FLTK has no page dialog and the print dialog sets the paper. Custom drawing that clips takes a `draw::Clip`: FLTK keeps a clip in logical pixels and reselects it at the scale of the moment, so a `Dev` clips to the innermost `Clip` in device pixels of its own. Every dialog centers on the main window and gets its close box (`dialogs::show_modal`, `run_modal`), questions use the message-box layout (`dialogs::ask_icon`, `message`, `prompt_titled`, `confirm_delete_titled`, `about`), check boxes, radios and arrow buttons are the Windows ones (`draw::check`, `radio`, `arrow`), menus take `draw::style_menu`, a Choice drops its list below the field (`combo::drop_below`), note boxes share `note_dialog::NoteBox`, and accelerator underlines hide until Alt (`mnemonics.cpp`; code that finds a menu item by its `&` path runs inside `mnemonics::with_originals`). Every widget callback, timer and worker thread sends a `Msg` to the main loop, so no callback borrows the app state. `palm-desktop --shot out.ppm` saves an offscreen capture at `FLTK_SCALING_FACTOR`, and `--shot-open "click:X,Y;rclick:X,Y;..."` first opens menus, lists and dialogs by posting mouse events to the app's own window (`shot.cpp`); test with `APPDATA` (Windows) or `XDG_CONFIG_HOME` pointing at a folder of copies, and never send simulated keys to the desktop. FLTK 1.4.5 builds from source through CMake FetchContent (offline: `-DFETCHCONTENT_SOURCE_DIR_FLTK=<an FLTK 1.4.5 source folder>`, e.g. the `fltk` folder of fltk-sys-1.5.23 in `~/.cargo/registry`), with GDI+ on Windows, and the 3.1.1 bitmaps of `desktop-cpp/assets/icons/` are embedded by CMake (`palm::assets`). PLAN.md's UI rules give the FLTK patterns: every window is an `Fl_Double_Window`, a custom handle or draw is a subclass that runs FLTK's handler and draw first, and a widget extended after building is a subclass the caller builds (`combo::Choice`, `text_edit::Editor` and `Input`, `records::RecordTable`). It uses OpenSSL, zlib, libcurl, nlohmann/json and doctest; `palm/text.hpp` holds the string and code point helpers, and no module keeps a copy; its case tables (`core/src/text_case.inc`) are generated data. `json::parse_value` and `json::dump` keep the values, float texts and error texts of the files the earlier apps wrote. This machine builds it with MSYS2 mingw64 (put `C:/tools/msys64/mingw64/bin` first on PATH): `cmake -S . -B build/all -G Ninja`, `cmake --build build/all`, `ctest --test-dir build/all`; warnings are errors. The CI `desktop-cpp` job checks `clang-format` 20, builds and tests on Windows amd64 (MSYS2) and Linux amd64 and arm64 (g++-14 on ubuntu-24.04), and starts palmsync for the server test on Linux amd64. It packages each build with `desktop-cpp/packaging/package.sh` (the program carries the app icon): on Windows an MSI from the WiX 3 source `packaging/palm-desktop.wxs` (the upgrade code of the Swing MSI, per-user, shortcut boxes) with the MSYS2 DLLs the program loads, which the job installs, starts with only the Windows folders on PATH, and removes; on Linux a tar.gz of the program and the icon (`palm-desktop-windows.msi`, `palm-desktop-linux-x86_64.tar.gz`, `palm-desktop-linux-arm64.tar.gz`). A tag `desktop-v*` gives the MSI its version and attaches the three packages to its release. The Linux build needs glibc 2.38 and the libstdc++ of GCC 13.2. `packaging/make-icon.py` draws the app icon. The port rules and the record of the phases are in `desktop-cpp/PLAN.md`.
- `sync-core/testdata/*.json` holds the test vectors of the desktop app's sync code: `VectorsTest` runs the Kotlin code on fixed inputs and compares the results with these files, and the C++ port (`desktop-cpp/core`) must give the same results. A missing file is written from the Kotlin output. A sync-core change that alters an output fails `VectorsTest`, which writes the new output to `sync-core/build/vectors/` (CI uploads both folders as `sync-core-vectors`): check it, copy it to `testdata/`, and change the C++ port to match in the same change.
- `gentoo/` is a Portage overlay with one ebuild, `app-office/palm-desktop-bin`, which installs the Linux package of a `desktop-v*` release (`palm-desktop-linux-x86_64.tar.gz` or `-arm64`). After each `desktop-v*` release, run `gentoo/bump.sh <version>`: it renames the ebuild to the version and writes its `Manifest` from the two packages of the release. Commit both and push, or Gentoo users stay on the old version.
- All phone modules use the same stack: Kotlin, plain Android Views (no AndroidX, no Compose, no XML layouts), no dependencies other than `:palm-ui` (and `:sync-core` for Date Book), minSdk 26, compileSdk 37, targetSdk 34 (35 forces edge-to-edge, which breaks the Palm full screen), JDK 17. AGP 9.2.1 builds Kotlin itself (built-in Kotlin), so the modules apply no Kotlin Android plugin and set `kotlin { compilerOptions }`; the root `build.gradle.kts` pins KGP and the Compose compiler plugin to 2.2.21. Two exceptions, asked 2026-11-09: Date Book takes `play-services-wearable` (the Wear Data Layer), and the watch app `:datebook:wear` alone uses AndroidX and Compose (Glance Wear and Remote Compose, alpha, pinned; minSdk, compileSdk and targetSdk 37).
- The repository has no Gradle wrapper. Use Gradle 9.4.1, as CI does: `gradle assembleRelease` (the shipped APKs), `gradle testDebugUnitTest`, and `gradle :datebook:app:testDebugUnitTest --tests <class>` for one test class.
- This Windows machine has no Gradle on PATH and no Android SDK, so you cannot build or test locally. Do not try, and do not report it. Verify by code review. CI builds and tests each push. A report ends with the changes ready to commit and push.
- Each `app/debug.keystore` is committed on purpose and signs both build types, so a new build installs over the old one and keeps the user's data. Do not remove it or change the signing config.
- CI (`.github/workflows/build-apk.yml`) checks `INVENTORY.md`, builds and tests the apps on each push (it installs SDK platform 37 first), and uploads `handheld.apk`, `palm-launcher.apk` and `watch.apk`. A tag `handheld-v*`, `launcher-v*` or `watch-v*` attaches that one app's APK to the GitHub Release of the tag.
- Code that both apps use belongs in `palm-ui`. Do not copy it into an app.
- User-facing text follows Palm OS wording.
- `INVENTORY.md` lists every screen, dialog, control, menu command and behavior of the Android apps, with the date and method of its last check against the Palm reference, a parity table of the record features across the views, and the rules found from faults. A UI change updates its rows in the same change, a fault found in one view is checked across its parity row, and `python3 tools/ui_inventory.py --check` must list no control. The CI build job runs that check first and fails on any missing row.

## palm-ui

- `Ui.kt`: `Palm` (the colors, `Palm.text` in Palm px, `Palm.textBold` (inside `Palm.views`, the bold and large fonts make all text bold), `Palm.intoCutout`, the Palm OS font from the palm-ui assets through `Palm.typeface`), `pp()`/`ppf()` (the shorter screen side is 160 Palm px), the view builders (`label`, `hbox`, `vbox`, `box`, `palmButton`, `popupTrigger`, `checkBox`, `field`, `PushGroup`), `LinedBackground` (the Palm dotted underline: `field()` takes it, and the Date Book rows and lined pages use it), `PalmDialog` (the base of all forms; `tips` puts the Palm Tips icon in the title), `popupList`, `ask`, `palmAlert`, `IconView` (the note, lock, untimed diamond and Tips icons are pixel copies of the handbook pictures), `symbols`, `Window.hideStatusBar()`, `TypingRoot` and `isTallScreen` (the keyboard stays open on a tall screen) and `ditherPaint()` (the Palm 50% gray).
- `Menu.kt`: the Palm III menu bar (`MenuBar`), `MenuItem`, `command()` and `commandKey()`.
- `ShortCuts.kt`: the Palm ShortCuts (`ShortCut`, `ShortCuts` with the defaults, `list`, `find`, `expand`, and the date and time hooks) and `EditText.palmShortCuts()`, which `field()` and `BackEdit` call. The launcher sets no list, so it has no ShortCuts.
- `Categories.kt`: `Context.editCategories`, the Palm OS Edit Categories form, used by Date Book and the launcher.
- `Palm.text` and `Palm.textBold` give the form font (`Palm.FORM_TEXT`, 16 Palm px), which dialogs, menus and pop-up lists always use, as on the Palm. Date Book builds its screens inside `Palm.views(size, bold)`, which applies its Font option; the launcher sizes its screen text with its own `font()`. The launcher sets `Palm.intoCutout`.
- Text in a fixed width stays on one line: a push cell grows to fit its label, a right-aligned form label has room to its left, a menu drop-down moves left to fit, a dialog button row puts its gaps between the buttons and narrows its buttons, then its gaps, when it is wider than the form (`PalmDialog.fitButtons`), and triggers and selectors end in an ellipsis. `popupList` gives its list's place in the coordinates of its trigger's window, so a list in a dialog opens at its trigger.
- Each window (activity, `PalmDialog`, `MenuBar`) calls `Window.hideStatusBar()`; a new window type must call it too.
