# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Layout

One jj repository (colocated with git, remote `rearman/palm-suite`) with one Gradle build of five modules, and the Go sync server. The Date Book and launcher histories came in by subtree merges from the archived repos `rearman/datebook` and `rearman/palm-launcher`. Read the `CLAUDE.md` of the app you change before you work in it.

| `datebook/`      | `:datebook:app`      | Date Book, To Do List, Memo Pad, Address Book and Prefs (the ShortCuts): five launcher icons, one APK                                                                                                                                                                 | `com.rearman.datebook`                         | 4 spaces     |

## Shared conventions

- `sync-server/` is a Go module with the standard library only, outside the Gradle build. The CI `server` job runs `gofmt`, `go vet` and `go test`. A tag `server-v*` attaches the linux amd64 and arm64 binaries to its release. This machine has no Go, so CI also verifies the server.
- `sync-core/` is a plain Kotlin/JVM module (JDK 17) with no runtime dependency; it uses the `org.json` that Android has built in, and its tests add `org.json`. CI tests `:sync-core:test` in the build job. Date Book's model, iCalendar and sync logic live in sync-core in the package `com.rearman.datebook`, so Date Book code uses them with no import. The Swing desktop app (`desktop/`, versions up to 0.23) is gone since the cutover to the C++ app in 0.24; its history stays in jj.
- `desktop-rs/` is a Cargo workspace outside the Gradle build: the Rust and fltk-rs port of the Swing app, whence the C++ app is ported; it is never released. `core/` (phase 2) is the port of sync-core: its tests check it against `sync-core/testdata`, port SyncRunnerTest and SyncSessionTest, and sync two devices through a real palmsync when `PALMSYNC_URL` and `PALMSYNC_TOKEN` are set. `app/` is the desktop app (`palm-desktop`). Phase 3 gave it the store and the settings: they read and write the `desktop-data.json` and `desktop.properties` of the Swing app, and a lock file keeps a second copy of the Rust app from overwriting the data (a Swing app up to 0.23 takes no lock, so do not run one beside them). Phase 4 gave it the shell: the main window, menus, toolbar, launcher bar, status bar, the Windows classic edges drawn in device pixels (`draw.rs`), and sync with Sync Options; each view shows a placeholder until its phase. Phase 5 gave it the Memo Pad (`memo.rs`) and the parts the other views reuse: the detail split (`split.rs`), the category drop-downs and Edit Categories (`category.rs`), the record clipboard and list menu (`records.rs`), the text-field menu and Edit state (`text_edit.rs`), and the modal dialogs (`dialogs.rs`, each runs its own event loop). Phase 6 gave it the Address Book (`address.rs`) and its dialogs (`address_dialog.rs`: Edit Address, Custom Field Labels); Dial opens a `tel:` link. The text-field menu (`text_edit::Field`) covers one-line fields too, and `records.rs` holds the list events that the record lists share. Phase 7 gave it the To Do List (`todo.rs`: the table, the details, Show Options and Purge; its rules of order, due labels and completion serve the Day view too), the date dialog (`date_picker.rs`) and the Note Editor (`note_dialog.rs`), which the Date Book reuses. Phase 8 gave it the Date Book: the Day view with its right pane and tabs (`date.rs`), the Week and Month views (`week.rs`, `month.rs`), Edit Event with Change Repeat and Select Time (`event_dialog.rs`), and the parts they share (`date_shared.rs`). Custom drawing that clips takes a `draw::Clip`: FLTK keeps a clip in logical pixels and reselects it at the scale of the moment, so a `Dev` clips to the innermost `Clip` in device pixels of its own. Phase 9 gave it Find (`find.rs`), Import and Export (`transfer.rs`), Print (`printing.rs`, through the system print dialog) and Options (`options.rs`); Page Setup stays gray, since FLTK has no page dialog and the print dialog sets the paper. A comparison with Palm Desktop 3.1.1 at 100% brought the look closer: every dialog centers on the main window and gets its close box (`dialogs::show_modal`, `run_modal`), questions use the message-box layout (`dialogs::ask_icon`, `message`, `prompt_titled`, `confirm_delete_titled`, `about`), check boxes, radios and arrow buttons are the Windows ones (`draw::check`, `radio`, `arrow`), menus take `draw::style_menu`, a Choice drops its list below the field (`combo::drop_below`), note boxes share `note_dialog::NoteBox`, and accelerator underlines hide until Alt (`mnemonics.rs` rewrites button, tab and menu labels, menu labels in C memory; code that finds a menu item by its `&` path runs inside `mnemonics::with_originals`). Two fltk-rs traps: `app::event_mouse_button()` panics when the last event was a key, so code compares `app::event_button()` with `view::LEFT` or `RIGHT`; and fltk-rs runs FLTK's own handler of a widget first, so a `handle` that must see an event first calls `super_handle_first(false)`. The plan of the phases left is `desktop-rs/PLAN.md`. Every widget callback, timer and worker thread sends a `Msg` to the main loop, so no callback borrows the app state. `palm-desktop --shot out.ppm` saves an offscreen capture at `FLTK_SCALING_FACTOR`, and `--shot-open "click:X,Y;rclick:X,Y;..."` first opens menus, lists and dialogs by posting mouse events to the app's own window (`shot.rs`; the C++ app has the same); test with `APPDATA` (Windows) or `XDG_CONFIG_HOME` pointing at a folder of copies, and never send simulated keys to the desktop. Its test `real_files_round_trip` checks copies of real files when `PALM_REAL_DATA` names their folder; the files never go into the repository. Run `cargo` in `desktop-rs/`. This machine has Rust with the GNU host (`~/.cargo/config.toml` names the MSYS2 compilers), so build and check it here. The CI `desktop-rs` job runs `cargo fmt --check`, `cargo clippy -D warnings`, `cargo test` (the Linux amd64 run builds and starts palmsync from `sync-server/` for the server test) and `cargo build --release` for Windows amd64 and Linux amd64 and arm64, uploads the app binaries of the three targets, and uploads Linux screenshots of the app at three scales.
- `desktop-cpp/` is a CMake project outside the Gradle build: the shipped desktop app since 0.24, the C++23 and FLTK port of the Rust app, which ports each module of `desktop-rs/` line by line and keeps its names. `core/` is the port of `desktop-rs/core`: one static library per module, with doctest tests that check it against `sync-core/testdata`, port the round and session tests, and sync two devices through a real palmsync when `PALMSYNC_URL` and `PALMSYNC_TOKEN` are set. `app/` (phase 3) holds the store, the settings and `platform` (the local zone, with the CLDR Windows table, and OS error texts as Rust shows them); they read and write the `desktop-data.json` and `desktop.properties` of the Swing and Rust apps, and `test_store` checks copies of real files when `PALM_REAL_DATA` names their folder. Phases 4 to 9 gave `app/` the whole UI, ported module by module from `desktop-rs/app/src` (the same file names; `date.rs` is split into `date.cpp` and `date_view.cpp`, which share `app/src/date_internal.hpp`) and linked into `palm-desktop`; FLTK 1.4.5 builds from source through CMake FetchContent (offline: `-DFETCHCONTENT_SOURCE_DIR_FLTK=<the fltk folder of fltk-sys-1.5.23 in ~/.cargo/registry>`), and the 3.1.1 bitmaps are embedded by CMake (`palm::assets`). PLAN.md's UI rules carry the fltk-rs mappings: every window is an `Fl_Double_Window`, a Rust handle or draw closure is a subclass that keeps fltk-rs's order (FLTK's handler and draw first), and a widget the Rust extends after building is a subclass the caller builds (`combo::Choice`, `text_edit::Editor` and `Input`, `records::RecordTable`). `desktop-cpp/tools/shots/run.sh <rust app> <c++ app> <out dir>` compares the two apps pixel by pixel in the 58 states of `steps.txt` (views, menus, lists, and dialogs) at three scales, from the synthetic store beside it; on Windows put `C:/tools/msys64/mingw64/bin` first on PATH. All match on Windows; the CI `desktop-shots` job runs it on Linux. It uses OpenSSL, zlib, libcurl, nlohmann/json and doctest; `palm/text.hpp` holds the helpers for what Rust's `str` and `char` have built in, and no module keeps a copy; its case tables are generated from the Rust standard library by `desktop-cpp/tools/gen_case`. `json::parse_value` ports serde_json's reader and `json::dump` its writer, so values, float texts and error texts match the Rust app. FLTK builds as fltk-sys builds it (GDI+ on Windows), so the two apps draw the same pixels. This machine builds it with MSYS2 mingw64 (put `C:/tools/msys64/mingw64/bin` first on PATH): `cmake -S . -B build/all -G Ninja`, `cmake --build build/all`, `ctest --test-dir build/all`; warnings are errors. The CI `desktop-cpp` job checks `clang-format` 20, builds and tests on Windows amd64 (MSYS2) and Linux amd64 and arm64 (g++-14 on ubuntu-24.04), and starts palmsync for the server test on Linux amd64. It packages each build with `desktop-cpp/packaging/package.sh` (the program carries the app icon): on Windows an MSI from the WiX 3 source `packaging/palm-desktop.wxs` (the upgrade code of the Swing MSI, per-user, shortcut boxes) with the MSYS2 DLLs the program loads, which the job installs, starts with only the Windows folders on PATH, and removes; on Linux a tar.gz of the program and the icon (`palm-desktop-windows.msi`, `palm-desktop-linux-x86_64.tar.gz`, `palm-desktop-linux-arm64.tar.gz`). A tag `desktop-v*` gives the MSI its version and attaches the three packages to its release. The Linux build runs on ubuntu-24.04 and needs glibc 2.38 and the libstdc++ of GCC 13.2. The app icons live in `desktop-cpp/assets/icons/` and `packaging/` (`packaging/make-icon.py` draws the app icon); the Rust app embeds them from there. The port rules are in `desktop-cpp/PLAN.md`. A UI change goes into both apps, so the `desktop-shots` check keeps passing.
- `sync-core/testdata/*.json` holds the test vectors of the Rust port (phase 1): `VectorsTest` runs the Kotlin code on fixed inputs and compares the results with these files, and the Rust port must give the same results. A missing file is written from the Kotlin output. A sync-core change that alters an output fails `VectorsTest`, which writes the new output to `sync-core/build/vectors/` (CI uploads both folders as `sync-core-vectors`): check it, copy it to `testdata/`, and change the Rust port to match in the same change.
- `gentoo/` is a Portage overlay with one ebuild, `app-office/palm-desktop-bin`, which installs the Linux package of a `desktop-v*` release (`palm-desktop-linux-x86_64.tar.gz` or `-arm64`). After each `desktop-v*` release, run `gentoo/bump.sh <version>`: it renames the ebuild to the version and writes its `Manifest` from the two packages of the release. Commit both and push, or Gentoo users stay on the old version.
- All Android modules use the same stack: Kotlin, plain Android Views (no AndroidX, no Compose, no XML layouts), no dependencies other than `:palm-ui` (and `:sync-core` for Date Book), minSdk 26, compileSdk and targetSdk 34, JDK 17.
- The repository has no Gradle wrapper. Use Gradle 8.7, as CI does: `gradle assembleRelease` (the shipped APKs), `gradle testDebugUnitTest`, and `gradle :datebook:app:testDebugUnitTest --tests <class>` for one test class.
- This Windows machine has no Gradle on PATH and no Android SDK, so you cannot build or test locally. Do not try, and do not report it. Verify by code review. CI builds and tests each push. A report ends with the changes ready to commit and push.
- Each `app/debug.keystore` is committed on purpose and signs both build types, so a new build installs over the old one and keeps the user's data. Do not remove it or change the signing config.
- CI (`.github/workflows/build-apk.yml`) checks `INVENTORY.md`, builds and tests both apps on each push, and uploads `handheld.apk` and `palm-launcher.apk`. A tag `handheld-v*` or `launcher-v*` attaches that one app's APK to the GitHub Release of the tag.
- Code that both apps use belongs in `palm-ui`. Do not copy it into an app.
- User-facing text follows Palm OS wording.
- `INVENTORY.md` lists every screen, dialog, control, menu command and behavior of the Android apps, with the date and method of its last check against the Palm reference, a parity table of the record features across the views, and the rules found from faults. A UI change updates its rows in the same change, a fault found in one view is checked across its parity row, and `python3 tools/ui_inventory.py --check` must list no control. The CI build job runs that check first and fails on any missing row.

## palm-ui

- `Ui.kt`: `Palm` (the colors, `Palm.text` in Palm px, `Palm.textBold` (inside `Palm.views`, the bold and large fonts make all text bold), `Palm.intoCutout`, the Palm OS font from the palm-ui assets through `Palm.typeface`), `pp()`/`ppf()` (the shorter screen side is 160 Palm px), the view builders (`label`, `hbox`, `vbox`, `box`, `palmButton`, `popupTrigger`, `checkBox`, `field`, `PushGroup`), `LinedBackground` (the Palm dotted underline: `field()` takes it, and the Date Book rows and lined pages use it), `PalmDialog` (the base of all forms; `tips` puts the Palm Tips icon in the title), `popupList`, `ask`, `palmAlert`, `IconView` (the note, lock, untimed diamond and Tips icons are pixel copies of the handbook pictures), `symbols`, `Window.hideStatusBar()`, `TypingRoot` and `isTallScreen` (the keyboard stays open on a tall screen) and `ditherPaint()` (the Palm 50% gray).
- `Menu.kt`: the Palm III menu bar (`MenuBar`), `MenuItem`, `command()` and `commandKey()`.
- `ShortCuts.kt`: the Palm ShortCuts (`ShortCut`, `ShortCuts` with the defaults, `list`, `find`, `expand`, and the date and time hooks) and `EditText.palmShortCuts()`, which `field()` and `BackEdit` call. The launcher sets no list, so it has no ShortCuts.
- `Categories.kt`: `Context.editCategories`, the Palm OS Edit Categories form, used by Date Book and the launcher.
- `Palm.text` and `Palm.textBold` give the form font (`Palm.FORM_TEXT`, 16 Palm px), which dialogs, menus and pop-up lists always use, as on the Palm. Date Book builds its screens inside `Palm.views(size, bold)`, which applies its Font option; the launcher sizes its screen text with its own `font()`. The launcher sets `Palm.intoCutout`.
- Text in a fixed width stays on one line: a push cell grows to fit its label, a right-aligned form label has room to its left, a menu drop-down moves left to fit, a dialog button row puts its gaps between the buttons and narrows its buttons, then its gaps, when it is wider than the form (`PalmDialog.fitButtons`), and triggers and selectors end in an ellipsis. `popupList` gives its list's place in the coordinates of its trigger's window, so a list in a dialog opens at its trigger.
- Each window (activity, `PalmDialog`, `MenuBar`) calls `Window.hideStatusBar()`; a new window type must call it too.
