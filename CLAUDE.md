# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Layout

One jj repository (colocated with git, remote `rearman/palm-suite`) with one Gradle build of five modules, and the Go sync server. The Date Book and launcher histories came in by subtree merges from the archived repos `rearman/datebook` and `rearman/palm-launcher`. Read the `CLAUDE.md` of the app you change before you work in it.

## Shared conventions

- `sync-server/` is a Go module with the standard library only, outside the Gradle build. The CI `server` job runs `gofmt`, `go vet` and `go test`. A tag `server-v*` attaches the linux amd64 and arm64 binaries to its release. This machine has no Go, so CI also verifies the server.
- `sync-core/` and `desktop/` are plain Kotlin/JVM modules (JDK 17). `sync-core` has no runtime dependency; it uses the `org.json` that Android has built in, and `desktop` adds `org.json`. CI tests `:sync-core:test` in the build job. Date Book's model, iCalendar and sync logic live in sync-core in the package `com.rearman.datebook`, so Date Book code uses them with no import. The `desktop` job runs `gradle --configure-on-demand :desktop:test :desktop:installDist` on Windows and Linux, and packages it with `jpackage`: an MSI on Windows (WiX 3, fixed upgrade UUID, version from the tag, shortcuts optional in the installer) and an app image tar.gz on Linux. The Linux job also packs the jars and the icon in `palm-desktop-jars.tar.gz` for the Gentoo ebuild. A tag `desktop-v*` attaches all three files to its release.
- `desktop-rs/` is a Cargo workspace outside the Gradle build: the Rust and fltk-rs port of the desktop app. `core/` (phase 2) is the port of sync-core: its tests check it against `sync-core/testdata`, port SyncRunnerTest and SyncSessionTest, and sync two devices through a real palmsync when `PALMSYNC_URL` and `PALMSYNC_TOKEN` are set. `spike/` (phase 0) tests sharp drawing at 125% and 150% display scale. `app/` is the desktop app (`palm-desktop`). Phase 3 gave it the store and the settings: they read and write the `desktop-data.json` and `desktop.properties` of the Swing app, and a lock file keeps a second copy of the Rust app from overwriting the data (the Swing app takes no lock, so do not run both). Phase 4 gave it the shell: the main window, menus, toolbar, launcher bar, status bar, the Windows classic edges drawn in device pixels (`draw.rs`), and sync with Sync Options; each view shows a placeholder until its phase. Phase 5 gave it the Memo Pad (`memo.rs`) and the parts the other views reuse: the detail split (`split.rs`), the category drop-downs and Edit Categories (`category.rs`), the record clipboard and list menu (`records.rs`), the text-field menu and Edit state (`text_edit.rs`), and the modal dialogs (`dialogs.rs`, each runs its own event loop). Phase 6 gave it the Address Book (`address.rs`) and its dialogs (`address_dialog.rs`: Edit Address, Custom Field Labels); Dial opens a `tel:` link. The text-field menu (`text_edit::Field`) covers one-line fields too, and `records.rs` holds the list events that the record lists share. Phase 7 gave it the To Do List (`todo.rs`: the table, the details, Show Options and Purge; its rules of order, due labels and completion serve the Day view too), the date dialog (`date_picker.rs`) and the Note Editor (`note_dialog.rs`), which the Date Book reuses. Phase 8 gave it the Date Book: the Day view with its right pane and tabs (`date.rs`), the Week and Month views (`week.rs`, `month.rs`), Edit Event with Change Repeat and Select Time (`event_dialog.rs`), and the parts they share (`date_shared.rs`). Custom drawing that clips takes a `draw::Clip`: FLTK keeps a clip in logical pixels and reselects it at the scale of the moment, so a `Dev` clips to the innermost `Clip` in device pixels of its own. The plan of the phases left is `desktop-rs/PLAN.md`. Every widget callback, timer and worker thread sends a `Msg` to the main loop, so no callback borrows the app state. `palm-desktop --shot out.ppm` saves an offscreen capture at `FLTK_SCALING_FACTOR`; test with `APPDATA` (Windows) or `XDG_CONFIG_HOME` pointing at a folder of copies, and never send simulated keys to the desktop. Its test `real_files_round_trip` checks copies of real files when `PALM_REAL_DATA` names their folder; the files never go into the repository. Run `cargo` in `desktop-rs/`. This machine has Rust with the GNU host (`~/.cargo/config.toml` names the MSYS2 compilers), so build and check it here. The CI `desktop-rs` job runs `cargo fmt --check`, `cargo clippy -D warnings`, `cargo test` (the Linux amd64 run builds and starts palmsync from `sync-server/` for the server test) and `cargo build --release` for Windows amd64 and Linux amd64 and arm64, uploads the spike and app binaries of the three targets, and uploads Linux screenshots of both at three scales. The Swing app in `desktop/` stays the shipped app until the cutover.
- `sync-core/testdata/*.json` holds the test vectors of the Rust port (phase 1): `VectorsTest` runs the Kotlin code on fixed inputs and compares the results with these files, and the Rust port must give the same results. A missing file is written from the Kotlin output. A sync-core change that alters an output fails `VectorsTest`, which writes the new output to `sync-core/build/vectors/` (CI uploads both folders as `sync-core-vectors`): check it, copy it to `testdata/`, and change the Rust port to match in the same change.
- `gentoo/` is a Portage overlay with one ebuild, `app-office/palm-desktop-bin`, which installs `palm-desktop-jars.tar.gz`. After each `desktop-v*` release, run `gentoo/bump.sh <version>`: it renames the ebuild to the version and writes its `Manifest` from the release. Commit both and push, or Gentoo users stay on the old version.
- All Android modules use the same stack: Kotlin, plain Android Views (no AndroidX, no Compose, no XML layouts), no dependencies other than `:palm-ui` (and `:sync-core` for Date Book), minSdk 26, compileSdk and targetSdk 34, JDK 17.
- The repository has no Gradle wrapper. Use Gradle 8.7, as CI does: `gradle assembleRelease` (the shipped APKs), `gradle testDebugUnitTest`, and `gradle :datebook:app:testDebugUnitTest --tests <class>` for one test class.
- This Windows machine has no Gradle on PATH and no Android SDK, so you cannot build or test locally. Do not try, and do not report it. Verify by code review. CI builds and tests each push. A report ends with the changes ready to commit and push.
- Each `app/debug.keystore` is committed on purpose and signs both build types, so a new build installs over the old one and keeps the user's data. Do not remove it or change the signing config.
- CI (`.github/workflows/build-apk.yml`) builds and tests both apps on each push and uploads `handheld.apk` and `palm-launcher.apk`. A tag `handheld-v*` or `launcher-v*` attaches that one app's APK to the GitHub Release of the tag.
- Code that both apps use belongs in `palm-ui`. Do not copy it into an app.
- User-facing text follows Palm OS wording.

## palm-ui

- `Ui.kt`: `Palm` (the colors, `Palm.text` in Palm px, `Palm.intoCutout`, the Palm OS font from the palm-ui assets through `Palm.typeface`), `pp()`/`ppf()` (the shorter screen side is 160 Palm px), the view builders (`label`, `hbox`, `vbox`, `box`, `palmButton`, `popupTrigger`, `checkBox`, `field`, `PushGroup`), `PalmDialog` (the base of all forms), `popupList`, `ask`, `palmAlert`, `IconView`, `symbols`, `Window.hideStatusBar()`, `TypingRoot` and `isTallScreen` (the keyboard stays open on a tall screen) and `ditherPaint()` (the Palm 50% gray).
- `Menu.kt`: the Palm III menu bar (`MenuBar`), `MenuItem`, `command()` and `commandKey()`.
- `ShortCuts.kt`: the Palm ShortCuts (`ShortCut`, `ShortCuts` with the defaults, `list`, `find`, `expand`, and the date and time hooks) and `EditText.palmShortCuts()`, which `field()` and `BackEdit` call. The launcher sets no list, so it has no ShortCuts.
- `Categories.kt`: `Context.editCategories`, the Palm OS Edit Categories form, used by Date Book and the launcher.
- Each app sets `Palm.text` from its own text size option before it draws. The launcher sets `Palm.intoCutout`.
- Each window (activity, `PalmDialog`, `MenuBar`) calls `Window.hideStatusBar()`; a new window type must call it too.
