# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Four Android apps after the Palm OS 3.5 Date Book, To Do List, Memo Pad and Address Book, and the Prefs app with the ShortCuts, in one APK. Each app has its own launcher icon and task. The Date Book and To Do List apps use the same records. All four apps use the one `Store` database. Kotlin, plain Android Views (no AndroidX, no Compose, no XML layouts), no dependencies other than the repository modules `:palm-ui` and `:sync-core` and one exception, `play-services-wearable` (the Wear Data Layer of `WearBridge`, which brings `androidx.core`). minSdk 26, compileSdk 37, targetSdk 34 (35 forces edge-to-edge), JDK 17. A call of an API above 26 sits behind an `SDK_INT` check. Version control is jj.

The watch app is `wear/` (`:datebook:wear`): the Date Book and To Do tiles for Wear OS 7 and the screen they open, with the applicationId `com.rearman.datebook` and the key `app/debug.keystore` (by path), which the Data Layer requires. It alone uses AndroidX: Tiles 1.6.2 and ProtoLayout 1.4.2 with its Material 3 (stable, pinned), `concurrent-futures-ktx` (`SuspendToFutureAdapter`, a tile request as a suspend function), `kotlinx-coroutines-android`, and `play-services-wearable`. minSdk, compileSdk and targetSdk 37. Up to 1.1 (2026-11-11) the two were Glance Wear widgets with Remote Compose; Glance Wear gives a widget only the 113 dp card that the watch makes for it, and pads it 8 dp at the top and bottom and about 13 dp at the sides (`WearWidgetDocument` wraps the content in `WearWidgetContainer`, with no way out), so they became tiles, which have the whole screen, as the Google tiles do. `AgendaListener` saves the agenda that `WearBridge` sends (`AgendaStore`, which also fetches the item when nothing is saved), `AgendaTileService` builds the tile of the appointments still to come (`WearAgenda.upcoming`: today's, then the later days'), `TodoTileService` the tile of the first open To Dos, and `AgendaTick` updates both at the next end of an appointment and at midnight (`Tiles.updateAll`, a request to the watch). `Tiles.kt` holds what both share, with their base `DateBookTileService`, which loads the agenda, sets the clock format and moves `AgendaTick` on each request, then calls the tile's `build` with the screen of `screen` (a request with no device configuration gets an empty one, 0 dp high, which drew a blank tile, so `screen` puts in the watch's own size, density and font scale and logs a warning under the tag `DateBookTile`); `AgendaTick` holds its process 3 s with `goAsync` for the update's bind. A tile is a Material 3 `primaryLayout`: the watch draws the app icon at the top, on a white disc, so the tiles take the dark icons `ic_agenda_tile` and `ic_todo_tile` and the app keeps the white ones; the title (the app name) goes under it; and the rows fill the main slot, with the side margins of a layout with an edge button (7.1% of the width, 192 dp on the Pixel Watch 5) and the bottom margin of one with no bottom slot (16.64% of the height). Each entry is a bubble of its own (`bubble`: light gray background, round corners, padding), black on light gray, the Date Book ones under a white centered header of their day (`header`). A tile cannot scroll, so `Fit` takes the rows that fit the main slot: the screen height less the layout's header (after `PrimaryLayout.kt` of protolayout-material3) and bottom margin; each text sets its line height to `Fit.LINE` times its size, so a row's height is known before the watch draws it. Its constants and `HEAD_SP`, `ENTRY_SP` and `CHECK_SP` are the values to tune on the watch. A tap anywhere but a check box (a header, a bubble, a To Do's text, or the layout's `onClick`) opens `AgendaActivity` (a `LaunchAction` with the extra `EXTRA_TODOS`), the watch screen in plain Android Views (the 7 days and the To Dos, with a launcher icon). A tap on a To Do's check box is a `LoadAction` with the id `done/<uid>/<nonce>` (the nonce is the time the tile was built): the tile asks for itself again, and that request calls `AgendaStore.markDone` if `AgendaStore.takeClick` has not seen the id and the To Do is still open, since a later request may carry the last clicked id again. On the screen a `CheckBox` does the same. `markDone` hides the To Do on the watch at once and puts the uids not yet settled in the Data Layer item `/done` for the phone's `WearListener`; an agenda that no longer lists a uid settles it. On the watch screen the check box and the text of a To Do are two views, so only the box completes it. The tiles use the system font.

## Build

The repository has no Gradle wrapper. CI (`.github/workflows/build-apk.yml`) uses Gradle 9.4.1 (AGP 9.2.1, Kotlin 2.2.21) on JDK 17:

```sh
gradle assembleRelease --stacktrace
```

Output: `app/build/outputs/apk/release/app-release.apk`, shrunk by R8 (`-dontobfuscate`, so stack traces keep their names) and signed with `debug.keystore`. CI runs on each push to `main` or `master`, on each push of a `v*` tag, and on manual dispatch. CI uploads the APK unzipped (`upload-artifact` with `archive: false`), so the artifact is the file itself. A workflow step first renames it to `handheld.apk`, or to `handheld-<tag>.apk` for a tag build, which is the artifact name. That mode accepts only one file, so keep the path exact. A tag build also attaches the APK to the GitHub Release of that tag, and creates the release when it does not exist.

JVM unit tests (JUnit 4) are in `app/src/test/`. The tests of the model, iCalendar, vCard and sync logic are in `sync-core/src/test/`. CI runs them after the build:

```sh
gradle testDebugUnitTest
gradle :sync-core:test --tests com.rearman.datebook.FreeTimesTest
```

The repository has no lint configuration.

`app/debug.keystore` is committed on purpose. Both build types sign with it, so a new build installs over the old one and keeps the user's data. Do not remove it or change the signing config.

## Architecture

All app source is in `app/src/main/java/com/rearman/datebook/`, except the model, iCalendar and sync logic, which are in the `sync-core` module (see **Shared logic** below).

- **One activity class, five apps.** `PrefsActivity` (`PrefsApp.kt`, the ShortCuts) is a subclass of `MainActivity` that only sets `isPrefsApp = true`. `TodoActivity` is a subclass of `MainActivity` that only sets `isTodoApp = true`. `MemoActivity` is a subclass of `MainActivity` that only sets `isMemoApp = true`. `AddressActivity` is a subclass of `MainActivity` that only sets `isAddressApp = true`. The manifest gives each one its own `taskAffinity`, icon and `singleTask` launch mode. `MainActivity` holds all screens. A `mode` field (`DAY`, `WEEK`, `MONTH`, `AGENDA`, `TODO`, `MEMO`, `ADDRESS`, `PREFS`) selects one. Cross-app jumps (`openTodoApp`, `openDateBook`, `openMemoApp`, `openAddressApp`) send intents with `EXTRA_*` extras (`EXTRA_MEMO` for Memo Pad, `EXTRA_ADDRESS` for Address Book), which `handleIntent` reads.
- **Full rebuild on each change.** `render()` removes all views and calls the `build*` function for the current mode. The UI keeps no state between renders other than the fields of `MainActivity`. After a record change, call `changed()` (it reschedules alarms, then renders) or `render()`.
- **Data** (`Store.kt`): `Store` is a singleton `SQLiteOpenHelper` on `datebook.db` with tables `events`, `todos`, `categories`, `memos` and `addresses`. It loads each table one time into an in-memory `MutableList`. `save`/`delete` write through to SQLite and update the list. `exportJson`/`importJson` read and write the backup format through `Backup` in sync-core, with memos and addresses included. The DB version is 4. `onUpgrade` version 2 adds the `memos` table and the per-app `categories` column (the Memo Pad categories). Version 3 adds the sync columns to all tables: `uid` (the same on every device; the default categories have fixed uids such as `default-0-business`), `rev` (last server revision, 0 = never synced), `dirty` (set by every write) and `deleted`. `delete` removes a row with `rev` 0 and makes any other row a tombstone with its text cleared. The `load*` queries skip tombstones. The models carry only `uid`; `dupKey` ignores it. Version 4 adds the `addresses` table and the Address Book categories (`categories` rows with app 2). Addresses and the app 2 categories sync like memos (kind "address"), and `dirtyRows` includes them. A later schema change needs a version increase and a migration. `Prefs` wraps the `prefs` SharedPreferences file.
- **Model** (`Model.kt`, in `sync-core`, same package): dates are epoch days (`Long`). Times are minutes after midnight (`Int`). `-1` means "no date". `Event` stores one first occurrence and repeat rules. `Recur.occursOn` expands them, and `Occ` is one event on one day. Exceptions (`exceptions` set of epoch days) give "Current" edits and deletes of a repeating event. `saveEventEdit` and `deleteEvent` in `MainActivity` split an event for Current, Future and All.
- **Alarms** (`Alarms.kt`): there is only one system alarm, set for the next reminder of all events. `Alarms.scheduleNext` finds it. `AlarmReceiver` shows the notifications and handles remind, snooze and OK actions. `BootReceiver` reschedules after boot, time change, time zone change and package update, and pushes the watch agenda. The alarm notification carries a Wear dismissal id (`alarm/<id>/<day>`), so OK or a dismiss on the phone or the watch clears both. On Android 16 and later, `scheduleNext` also sets a second alarm (`ACTION_LIVE`) for the next start or end of a timed event with Alarm on, and `refreshLive` shows a Live Update (channel `datebook_now`, tag `live`, an ongoing notification whose chronometer counts down to the end, promoted to the status bar chip only on API 36.1 and later, since the promotion methods are absent on 36.0; a notification the system rejects is left out, so the app never stops in `onResume`) for each such event in progress and removes the others, so an edit or delete through `changed()`, or a sync that applied records (`SyncEngine` calls `scheduleNext` itself), clears a stale one. An inexact third alarm (`ACTION_DAY`) at midnight runs `scheduleNext` and pushes the watch agenda. `scheduleNext` and `show` set `Fmt.h24` from the system, since a receiver can run in a process with no activity. Event times in ms come from `Recur.millis` (wall-clock minutes, so DST keeps the time).
- **Watch** (`WearBridge.kt`): puts the Data Layer item `/agenda`, a JSON payload of today and 6 more days (events in Day view order; the open To Dos due by the last day and those with no date, in To Do List order through `Store.sortTodos`, each with its uid), in the format of `WearAgenda` in sync-core, the one codec of both sides, for the watch app in `wear/`. Hide leaves private records out; Mask sends them as "Private" with no uid, so the watch gives them no check box. `WearListener` (same file) takes the item `/done`, the uids of the To Dos checked on the watch, and completes each open one on the main thread through `Store.complete` (the rule of `completeTodo`, with Record Completion Date); with no activity in the process it schedules the sync job itself, then pushes the agenda and renders an open screen through `SyncEngine.onApplied`. `pushSoon` (app open) pushes 2 s after `Store.onWrite` and a Security change; `push` (at once, for receivers and jobs) runs after a sync that applied records, at boot, and at midnight (`Alarms.ACTION_DAY`).
- **UI kit:** the shared `palm-ui` module (see the root `CLAUDE.md`) holds the Palm colors, font, Palm px, view builders, `PalmDialog`, `popupList` and the menu bar. Each Date Book file imports `com.rearman.palmui.*`. `MainActivity.render()` builds the screen inside `Palm.views`, which applies the Font option; dialogs, menus and pop-up lists keep the form font. Use these builders for new UI. Use `dp()` only for gesture distances.
- **ShortCuts:** `palm-ui` `ShortCuts.kt` holds the list logic. `Prefs.shortCuts` saves the list. `MainActivity.onCreate` sets `ShortCuts.list`, `date` and `time`. The Prefs app (`buildPrefs` in `PrefsApp.kt`) lists and edits them, as the Palm Prefs ShortCuts panel does.
- **iCalendar** (`ICal.kt`, in `sync-core`, same package): `ICal.export` writes events with floating local times. `ICal.parse` reads a `.ics` file into events, splits a timed event that goes past midnight into one event for each day, and counts the file events it had to simplify. `Store.addEvents` adds them less duplicates (`dupKey`). The import in `MainActivity.onActivityResult` reads a file that starts with `BEGIN:VCALENDAR` as iCalendar and any other file as a backup.
- **Shared logic** (`sync-core` module, package `com.rearman.datebook`, with its tests in `sync-core/src/test/java/com/rearman/datebook/`): `Model.kt`, `ICal.kt`, `VCard.kt` (vCard 3.0 read and write for the Address Book), `SyncCodec.kt` (record JSON), `SyncLogic.kt` (`SyncLogic.decide`, the keep-both table), `Backup.kt` (`Backup.write` and `Backup.read`, the Date Book backup file of both apps, with addresses and the three category lists), `WearAgenda.kt` (the watch agenda payload, written by `WearBridge` and read by the watch app; Android only, so the desktop port has no copy), `SyncKeys.kt` (`SyncKeys.firstKey` and `keyFromMeta`, the passphrase key setup), `SyncSession.kt` (`SyncSession`, the sync round loop, with the worker and UI threads given by each app) and the sync round `SyncRunner` with the `SyncStore` interface. The palmsync client is `SyncCrypto` (PBKDF2 and AES-GCM) and `SyncClient` (HTTP), in package `com.rearman.palmsync`.
- **Sync** (`SyncEngine.kt`): the Android part of sync. It holds the threads, `KeyVault` (Keystore-wrapped key and token), `Prefs` and the jobs, and it adapts `Store` to `SyncStore`. SyncEngine runs the rounds through `SyncSession` and sets up the key through `SyncKeys`. `SyncJob` (JobScheduler: hourly, and a backup 30 s after `Store.onWrite`; the in-app sync runs 1 s after `Store.onWrite` through `SyncEngine.requestSoon`, and in `onResume` through `SyncEngine.request`) and `SyncForm.kt` (Options > Sync...) are part of it too. Network work runs on a worker thread; Store work runs on the main thread. `Store` sync functions: `dirtyRows`, `syncRow`, `markSynced`, `putRemote`, `dropRemote`, `resetSync`.
- `Grids.kt`: custom-drawn `WeekGrid` and `MonthGrid` views, and `lanes()` for overlapping time bars. `Details.kt`: the event and to-do details dialogs, and the Options dialogs (as `MainActivity` extension functions). `Pickers.kt`: date, time and repeat dialogs. `Memo.kt`: the Memo Pad screens (extension functions of `MainActivity`), and `linedPage`, the lined page of the Memo and Note views. `Note.kt`: the Palm Note view of all four apps. `noteOpen` puts it over the current screen: `render()` builds it in place of the mode, and Done or Back saves the note through the opener's callback. `noteIcon` is the tappable note icon of the record lists, and `maskedBar` the masked record (the 50% gray bar and the lock). `Security.kt`: Change Security, the Hide and Mask confirmations, the password (`Password`, a salted PBKDF2 hash in `Prefs.password`, tested by `PasswordTest`) and Show Private Records (`askPassword`).
- Address Book: `AddressList.kt` (the list and Look Up), `AddressView.kt`, `AddressEdit.kt`, `AddressDialogs.kt` (the dialogs and Phone Lookup) and `AddressShare.kt` (share, vCard import and export, `VcfProvider`, a minimal FileProvider because there is no AndroidX). These are extension functions of `MainActivity`.

## Conventions

- User-facing text and documentation follow Palm OS wording (menu names such as Record, Edit, Options; "Purge", "Security", "Show Options").
- `README.md` is user documentation, written in Simplified Technical English. Keep it current when a feature changes.
