# Open fault: Date Book crashes at every start (2026-11-09)

A handoff note for the next Claude session. Delete this file when the fault is fixed.

## Symptom

On the user's phone (Android 16 or later, with the Pixel Watch 5 paired), with `handheld.apk` from CI run 42707059194 (master at `1d0ac98`, Date Book 1.16):

1. The user made a timed event with Alarm on, 3 minutes in advance.
2. The alarm rang.
3. After the alarm, the user changed the event's time to a time in the past.
4. The app crashed. It crashes again at every start, also after a phone reboot.
5. The desktop app and the watch widget still show the old event time, so the edit never synced or reached the watch.

## What is known

- `MainActivity.onResume` calls `Alarms.scheduleNext` at every start (`MainActivity.kt`, `onResume`), and `changed()` calls it after every edit. `BootReceiver` calls it at boot. A fault in it that depends on the data would crash every start, as seen.
- `scheduleNext` was rewritten in commit `55870ff` ("Show the event in progress as a Live Update ..."): `nextDay`, the `ACTION_LIVE` and `ACTION_DAY` alarms, and `refreshLive`, which posts a promoted ongoing notification (channel `datebook_now`, tag `live`) for each alarmed timed event in progress. Only `SecurityException` is caught around `nm.notify`.
- The edit never reached the server or the watch. `Store.onWrite` starts a sync after 1 s and the watch push after 2 s, so the process likely died before the edit was saved, or within 1 s of it.

## Leading theory (not confirmed)

The crash came first, and the edit was lost with it. When the event started, `ACTION_LIVE` fired, and `refreshLive` built and posted the Live Update. Something in that path threw an exception other than `SecurityException`. Suspects, in order:

1. `nm.notify(LIVE_TAG, ...)` rejecting the promoted notification (`setRequestPromotedOngoing`, `setShortCriticalText`, the count-down chronometer, `setTimeoutAfter`, and `setPublicVersion` together).
2. `nm.canPostPromotedNotifications()` or `Notification.Builder.setShortCriticalText` / `setRequestPromotedOngoing` failing on this build of Android.
3. A fault in `nextDay` or the live-alarm math for an event in progress.

While the event stays in progress, every start reruns `refreshLive` and crashes again. If this is right, the app starts again after the event's original end time.

## Next steps

1. Get the stack trace. Connect to the phone over Wireless debugging (`adb pair`, `adb connect`), start Date Book once so it crashes, then run:
   ```sh
   adb -s <phone ip>:<port> logcat -b crash -d | tail -60
   ```
   The crash buffer empties at reboot: start the app first.
2. Fix the cause at its root in `Alarms.kt`. Whatever it is, a Live Update must never stop the app: wrap the posting in `refreshLive` so that a refused Live Update falls back to an ordinary notification or none, and the alarm logic and the app still run.
3. Recheck the alarm still fires at its advance time, Remind repeats, OK and Snooze, and the Live Update shows and leaves at the start and end (see `datebook/CLAUDE.md`, **Alarms**).
4. Ask the user whether the edit to the event's time was lost, and to make it again after the fix.
